**迁移落点**：`kda_test/turbo_chunk_kda`（fp32）、`turbo_chunk_kda_fp16`、`turbo_chunk_kda_bf16`

> **⚠️ 工具链口径（2026-09-23 更正）**：本文档早前数据混用两套工具链。**只有下面标注「3.2.1」的数字才是交付口径**
> （conda `autotriton`，`triton-ascend 3.2.1`）；未标注的迁移过程数据是在默认 `python3`
> （**`triton-ascend 3.2.2+dev`**）下测得，与交付口径**不可比**（同一 kernel 差异可达 67%，见 §5.3）。

| 参考优化点 | 参考自报收益 | 本机迁移结果 | 处置 |
|---|---|---|---|
| K1 一维 grid + 每核连续区间工作划分 | 1.37× | **1.148 vs 1.374 ms = −16.4%**（三树一致，**3.2.1 口径**） | ✅ **采纳** |
| K2 一维 grid + head-major | 1.08× | 9.546 vs 9.314 ms = **+2.4%（回归）** | ❌ 不采纳 |

| K6 一维 grid + 每核连续 | 1.04× | 3.702 vs 3.678 ms = +0.65%（回归） | ❌ 不采纳 |

**一句话结论**：参考的三处优化里只有 **K1 的工作划分思路**能在本机兑现（交付口径 **−16.4%**）；
K2/K6 的 block pointer 路线要么回归、要么直接算错。但迁移过程本身有额外收获：
发现并修复了 **2 个交付缺陷**（fp16 树 K2 精度不达标、K4 的 `beta` 越界读致 fp16 NaN），
并从「核数/工作划分」这条线索出发拿到 **1 项新优化（K3 `NP=2`，交付口径 −18.5%）**；
K1 换成一维 grid 后还**顺带解除了 coreDim 65535 限制**（最大 case `A_B4_H8_T131072`
的 K1 由"预检拒绝"变为实测通过，见 §1）。

**全量回归**（106 case × 6 kernel = 636 行，模式 A，3.2.1 口径）：fp32 / bf16 **各 627/636**，
失败清单两者完全一致 —— 只剩先前已有的声明式限制（4 行 grid 超限 + 5 行 K=32 不支持），
**无新增数值回归**（见 §6.2）。fp16 在交付口径下另暴露出**交付版既有的设备 trap 缺陷**
（`T%64≠0` 时 K4 触发 aivec trap），原树 431/636、打 workaround 后 627/636 —— 详见
`TEST_REPORT_RETEST_20260923.md` §6。

## 1. K1 `gate_chunk_cumsum` —— 采纳（3.2.1 口径 −16.4%）

### 迁移内容

参考做法是把三维 grid `(cdiv(K,BS), num_chunks, B*H)` 换成**一维 grid = 核数**，
每个核领取一段**连续**的工作区间，核内用 `for` 顺序消费，从而把每个 program 的
启动/收尾开销摊薄到一整段连续工作项上。

本仓实现的差异（三棵树 `turbo_gate_chunk_cumsum_kernel.py` 同步）：

1. **核数从设备取，不写死**：`_vector_core_num()` 读
   `torch_npu.npu.get_device_properties(0).vector_core_num`（本机 56），
   取不到时回退 910B2 的 48。参考硬编码 48。
2. **修正截断除法丢工作项**：参考的 `per_core = WORK // num_programs` 是截断除法，
   当 `total % ncore != 0` 时会**静默丢掉最后 `total % ncore` 个工作项**。
   本实现改为 ceil 除法 + `tl.minimum(total, (pid+1)*per_core)` 截断。
3. 保留原有显式掩码（未采用参考的"去掩码"做法 —— 参考收益分解里该步只贡献 1.27/1.23，
   而换 block pointer 在本工具链上有 D1/D4 风险，不值得为 <4% 引入）。

开关：`K1_MODE`（1=新划分，0=旧三维 grid），默认 1。

### 验证

**交付口径（3.2.1）A/B 实测**：

| 树 | `K1_MODE=0`（三维 grid） | `K1_MODE=1`（一维 grid） | 变化 |
|---|---|---|---|
| fp32 | 1.374 ms | **1.148 ms** | **−16.4%** |
| fp16 | 1.195 ms | **0.943 ms** | **−21.1%** |
| bf16 | 1.374 ms | **1.149 ms** | **−16.4%** |

（早期在 3.2.2+dev 上测得 1.517 → 1.479 ms = −2.5%，三树一致，现按交付口径更正。）

精度：`K1_MODE=1` 与 `=0` 的 max_diff 完全相同（fp32/bf16 6.104e-05，fp16 9.613e-03），
selftest 与目标 case 均 PASS。

### 为什么参考是 1.37× 而本机兑现 1.22×

参考 `REPORT.md:365-368` 给出的 K1 增益分解是：

| 阶段 | 耗时 | 累计加速比 |
|---|---|---|
| 原始基线 | 1.999 ms | 1.00× |
| 固定 48 核 grid + 关多缓冲 | 1.622 ms | 1.23× |
| 换 block pointer / 去掩码 | 1.579 ms | 1.27× |
| **每核连续工作划分** | **1.459 ms** | **1.37×** |

可见参考 1.37× 中**最大的单项是"核数适配"**，而它的基线本身是一个未做核数适配的版本。
本仓 turbo K1 迁移前的三维 grid 已做过部分核数适配，故只能兑现工作划分本身那一档
——交付口径下实测 **−16.4%（1.22×）**。这不是迁移失败，而是基线不同。

### 核数扫描（`K1_MODE=1`，3.2.2+dev 口径）

| grid | 28 | **56** | 112 | 224 | 448 |
|---|---|---|---|---|---|
| 耗时 | 2.950 ms | **1.478 ms** | 1.482 ms | 1.482 ms | 1.482 ms |

56（vector 核数）是必要的；再多核只是空转（1.478 → 1.482）。
block pointer、T 常量化、多缓冲在本 kernel 上没有额外收益。

### 附带收益：解除 K1 的 coreDim 限制（最大 case 由"不支持"变为可跑）

原三维 grid 展平后是 `cdiv(K,BS) · cdiv(T,BT) · B·H`，随 shape 线性增长；一维 grid 恒为
`min(total, 56)`，与 shape 无关。因此 `A_B4_H8_T131072`（展平 65536 > 65535）
**K1 从"启动即失败"变成正常出结果**：

| | K1 row（`A_B4_H8_T131072`, B=4 T=131072 H=8 K=V=64） |
|---|---|
| 迁移前 | `不支持`: grid(flattened)=65536 超过 NPU coreDim 上限 65535（未跑 kernel） |
| 迁移后 | `max_diff=5.722e-06` **OK** |

独立的直接调用复核（三棵树同源 K1，shape 取 B=4 T=131072 H=8 K=128）：
`max_diff=6.676e-06` OK。

> 该 case 的 K2/K3/K4/K6 仍受各自 grid 限制（它们的展平公式未变，确实超限），
> 所以整 case 仍不能全绿；但 K1 这一行现在是**实测通过**，而非被预检拒绝。

对应的 harness 修正见 §6.2。

## 2. K2 `token_parallel` —— 不采纳

K2 是本链最大的单核开销（9.31 ms），参考对它有两处优化：
一维 grid + head-major 工作划分、以及 block pointer 载入/写出。**两者在本机都不能采纳。**

### 2.1 一维 grid 单独迁移是回归

只把工作划分换成一维 grid + 每核连续（其余与交付版 hm2 完全一致，变体 `v4`）：

| 实现 | 目标 case | 全部 7 个测试 shape |
|---|---|---|
| v0 hm2（交付版） | 9.314 ms | PASS 2.98e-07 |
| **v4（仅换工作划分）** | **9.546 ms（+2.4%）** | PASS（全部正确） |

正确性没问题，但**方向与 K1 相反**：K1 上有效的划分在 K2 上是回归。
原因是一维 grid 把程序数从 hm2 的 1536 个压到 28 个（cube 核数），并行度大幅下降。

### 2.2 block pointer 载入在本工具链上产生**非确定性**错误

把 q/k/g 的载入换成 `tl.make_block_ptr`（其余与 v4 相同，变体 `v6`）：

| 实现 | 内核耗时 | 正确性 |
|---|---|---|
| v0 hm2 | 9.314 ms | PASS |
| **v6（block pointer 载入）** | **2.487 ms（3.75×）** | **FAIL** |

单看耗时是 3.75× 的巨大收益 —— **但结果全错，而且是"每次跑都不一样"**：

```
v6 目标 case，同一二进制、同一输入，连跑两次：
  第 1 次: 5.731e-01     第 2 次: 5.744e-01
  T16384_H2: 1.788e-07 (OK)  →  4.771e-01 (FAIL)   ← 同 shape 两次结果一个通过一个失败
```

全部 7 个 shape 的 max_diff 在两次运行间都不同 → **这是数据竞争，不是地址算错**。

**消融：已排除的候选原因**

| 假设 | 实验 | 结果 |
|---|---|---|
| `tl.range` 软件流水线导致 | `NS=1`（关流水线） | 仍非确定 |
| 后端自动多缓冲导致 | 启动级 `num_stages=1`（→ `--enable-auto-multi-buffer=False`） | 仍非确定 |
| block pointer 本身不支持跨步 | 最小独立探针（见下） | **正确且确定** |

**最小独立探针**（无循环、单 block pointer、与显式跨步 `tl.load` 逐元素对比）：

```
iter0..3  explicit==ref:True   bp==ref:True   bp_vs_explicit_maxdiff:0
```

→ **block pointer 的跨步解码本身是对的**：在本工具链上单独使用时与显式载入逐位一致、连跑 4 次确定。
竞争出现在「**循环内的 block pointer 载入 + 该 kernel 的其余结构**」这个组合里，
而非 block pointer 这一形式本身。已排除流水线与多缓冲两个常见诱因，根因未定位到具体 pass。

**同时排除的其它变体**（全部 FAIL）：

| 变体 | 说明 | 结果 |
|---|---|---|
| v1 hm3 | kernel 内 `tl.gather` | FAIL 4.721 |
| v2 | 参考原文照搬（1D grid + block ptr + 块内 gather） | FAIL 4.408 |
| v3 | 同 v2 但走 hm2 语义 | FAIL 7.311 |
| v7 | v6 + block pointer 写出 | FAIL 5.731 |
| v8 | v7 + 一维跨步 β block pointer | FAIL 4.549e-01 |
| v10/v11 | 写地址侧取模收拢（kernel 内消除 epilogue） | FAIL 4.598 |
| v12 | v4 原文 + 仅改 Akk 写出为掩码散写 | FAIL 4.598 |
| v13 | v12 但列地址连续（单变量对照） | FAIL 3.375 |
| v5 | `tl.reshape` 用于 dot 输出 | 崩溃 `ERR99999` |

v12/v13 这组对照说明：**带掩码的二维 store 本身就是坏的**（v12 只改了 store 就失败；
v13 把列地址换回连续、只留同一张掩码，仍失败）—— 缺陷在掩码 store，不在取模寻址。

### 2.3 结论

参考 K2 的真实收益只有 **1.08×**（9.466 → 8.742 ms，910B2），并非 3.75×；
在本机，能正确运行的那条路线（工作划分）是 **+2.4% 回归**，
能带来 3.75× 的那条路线（block pointer）**结果错误**。**K2 优化点不采纳。**

## 5. 由迁移线索启发的新优化

K2/K6 的迁移没有收益（与用户预设分支一致），转而在迁移过程中暴露出的线索上继续挖，得到 2 项：

### 5.1 K3 截断级数 `NP=2` 提速 18.5%（HM 结论按交付口径更正）

> **⚠️ 更正（2026-09-23）**：本节早期结论「交付默认 `HM=16` 编译失败、只有 `HM=1` 能编译」是在
> **triton-ascend 3.2.2+dev**（默认 `/usr/local/python3.11.10/bin/python3`）下得出的，**不适用于交付口径**。
> 在 **conda autotriton / triton-ascend 3.2.1** 上复测：`HM=16` **编译正常**，且 `HM=16/NP=2` 才是最优组合。
> 详细数据见 `TEST_REPORT_RETEST_20260923.md` §5.2。

K1 的线索是「**核数/并行度没有对齐目标机就会踩坑**」，顺着这条线扫了截断级数 `NP`
（目标 case，交付口径 3.2.1，msprof）：

| 配置 | 目标 case max_diff | 门槛(<1e-2) | msprof |
|---|---|---|---|
| HM=16 / NP=3（出厂默认） | 4.768e-07 | PASS | 10.692 ms |
| **HM=16 / NP=2（本次采用）** | **3.311e-04** | **PASS（30× 余量）** | **8.711 ms（−18.5%）** |
| HM=32 / NP=3 | — | PASS | 10.800 ms |
| HM=8 / NP=3 | — | PASS | 10.850 ms |
| HM=1 / NP=2 | — | PASS | 11.209 ms |
| HM=1 / NP=3 | — | PASS | 13.156 ms |
| HM=16 / NP=1 | 4.463e-02 | FAIL | 6.822 ms（不可用） |

即：**HM 维持出厂默认 16 最优**（HM=1 反而慢 29%），收益全部来自 `NP=3 → 2`。

`NP=2` 比 `NP=3` 少 2 个 dot。精度代价只在 fp32 树上可见：

| 树 | NP=3 | NP=2 |
|---|---|---|
| fp32 | 4.768e-07 | 3.311e-04 |
| fp16 | 4.977e-04 | **4.977e-04（完全相同）** |
| bf16 | 3.609e-03 | **3.609e-03（完全相同）** |

fp16/bf16 树上两者**逐位相同** —— 误差由输入量化主导，截断级数不贡献误差。
故 `NP=2` 在低精度树上完全免费，在 fp32 树上仍在门槛内 30 倍。

**已应用**：三棵树 `_NP` 默认改 2；`_HM` **保持交付默认 16**（HM=1 在 3.2.1 上更慢，不要改回 1）。
两处均带注释标注工具链口径。

### 5.2 fp16 树 K2 分离式 exp2 溢出（交付缺陷，精度 55× 且零性能代价）

K2 迁移过程中发现的**存量交付缺陷**：fp16 树全链目标 case 上 **K2 不达标**。

根因是分离式写法 `Aqk[i,j] = q_i·exp2(g_i) · k_j·exp2(-g_j)` 与 fp16 下采样的组合：

```python
qe = qc * tl.math.exp2(gc)                                    # fp32
ke = kc * tl.math.exp2(-gc)                                   # fp32, 实测可达 4.7e7
ke = tl.minimum(tl.maximum(ke, -65504.0), 65504.0)            # 饱和保护
Aqk_full = tl.dot(qe.to(tl.float16), tl.trans(ke.to(tl.float16)))   # ← 下采样到 fp16
```

链内实测 `g ∈ [-25.5, -0.014]` → `exp2(-g)` 最大 **4.666e7**，
**远超 fp16 上限 65504**；同时 `exp2(g)` 最小 2.1e-8，在 fp16 下下溢为 0。
饱和保护挡住了 inf/nan，但把真实值 4.7e7 截成 65504，小值则整体归零 →
Aqk/Akk 相对误差最大 35%。

这解释了为什么**只有 fp16 树挂**：

| 树 | dot 操作数类型 | `exp2(-g)` ≤ 4.7e7 vs 该类型上限 | 链内 K2 |
|---|---|---|---|
| fp32 | fp32 | 3.4e38 — 安全 | PASS 1.490e-07 |
| bf16 | bf16 | 3.4e38 — 安全 | PASS 6.033e-03 |
| **fp16** | **fp16** | **65504 — 溢出** | **FAIL 3.808e-02** |

**修复**：dot 操作数保持 fp32（不做 fp16 下采样），饱和保护随之移除——它只对已弃用的
fp16 dot 路径必要，在 fp32 下反而会把真实的 4.7e7 截成 65504。

**效果**：

| | 链内目标 case | 独立 test | msprof |
|---|---|---|---|
| 修复前 | **FAIL 3.808e-02** | — | 9.444 ms |
| 修复后 | **PASS 6.864e-04（精度 ↑55×）** | PASS 4.904e-04 | **9.443 ms** |

**性能代价为零**（9.443 vs 9.444 ms）—— K2 是访存瓶颈（跨步载入），不在 cube 上，
所以 fp32 dot 不花钱。

**bf16 树不适用该修复**：试过 bf16 / fp32 两种 dot 操作数，max_diff
**完全相同**（3.423e-03），说明 bf16 的误差全部来自输入/输出量化而非 dot 操作数下采样。
既然无收益，**bf16 树不做改动**。

### 5.3 K4 `recompute_w_u`：`beta` 漏 mask 导致的越界读（fp16 树 NaN，全量回归 8 例）

**现象**：全量回归里 fp16 树有 8 个 case 的 K4 行是 `nan`（`max_diff` 为 NaN，非数值超差），
fp32/bf16 同 case 全 OK。8 个 T 全部满足 `T % 64 ≠ 0`：
`T = 1025, 2049, 8193, 16385, 32769, 65537, 131071, 100000`。

**定位**（用 harness 自己的 `_derive_inputs` 复现，再逐 tensor 看 NaN 位置）：

| 张量 | NaN 元素数 | 位置 | 说明 |
|---|---|---|---|
| `w` = A @ (k·β·exp2(gk)) | 256 | 全部在 `t = T-1` 行 | 最后一个 chunk 的唯一有效行 |
| `u` = A @ (v·β) | 256 | 同上 | 同上 |
| `kg` = k·exp2(gk_last − gk) | **0** | — | **不乘 β** |

`w`/`u` 都乘 `beta`、`kg` 不乘 → 嫌疑锁定在 `beta`。核对 kernel：`k`、`v`、`gk`、`A` 四个输入
在 `T_FULL=False` 时都有 mask 分支，**只有 `beta` 是裸 load**：

```python
b_b = tl.load(p_beta + (base + o_bt) * s_beta).to(tl.float32)   # 无 mask
```

`beta` 形状是 `[B, T, H]`（只有 T 行，无 padding），而 `T % 64 ≠ 0` 时最后一个 chunk 的
`base + o_bt` 会取到 `T … NT*64-1`，**越过张量末尾**读到相邻内存。脏位在 fp16 下极易解码为
NaN；即使 `k`/`v` 已被 mask 成 0，后续 `0 * NaN = NaN` 把 `b_kb`/`b_vb` 整行污染，
再经 `tl.dot(b_A, ·)` 传染到唯一有效行。fp32/bf16 之所以"看着正常"，
只是因为脏位在 f32/bf16 下几乎不会解码成 NaN（NaN 编码占比极高→极低）。

> 顺带说明：先怀疑并给 `b_A` 的 load 补了行/列 mask（它同样是越界读），
> **实测输出逐位不变** —— 这反过来排除了 `b_A`，把范围收缩到唯一的另一条路径 `beta`。
> 两处 mask 都已保留：`beta` 是功能性修复，`b_A` 是消除越界读本身（无行为变化）。

**修复**（三棵树同改，`T_FULL=True` 分支一字未动）：

```python
if T_FULL:
    b_b = tl.load(p_beta + (base + o_bt) * s_beta).to(tl.float32)
else:
    b_b = tl.load(p_beta + (base + o_bt) * s_beta, mask=m_t, other=0.0).to(tl.float32)
```

`other=0.0` 与 torch 参考一致 —— 参考实现把 `beta` 零填充
（`turbo_recompute_w_u_torch` 的 `betaf = torch.cat([betaf, zf(...)])`），
所以 padding 行的 `kb`/`vb` 在参考里本来就是 0，mask 后**数值语义相同**。

**效果**：

| | 修复前 | 修复后 |
|---|---|---|
| `B_T1025` K4 `w` / `u` max_diff | `nan` / `nan` | **1.949e-04 / 2.797e-04** |
| `B_T2049` K4 `w` / `u` max_diff | `nan` / `nan` | **2.068e-04 / 3.299e-04** |
| fp16 全量回归 | 619/636 | **627/636**（8 例 `nan` 全部转 OK）※ |

**这不是 bench 专有问题**：真实推理里只要 `T % 64 ≠ 0`，fp16 树的最后一个 token 的
`w`/`u` 就是 NaN，会一路传到 K5/K6 污染输出。属于**交付缺陷修复**，非收益项。

**性能**：目标 case `T = 16384 = 64×256` → `T_FULL=True`，编译出的代码路径完全未变，
不加 mask、不引入分支。故对计时**零影响**（§6.1 表未随之改动）。

> **※ 口径更正（2026-09-23）**：上表 ③ 列是在 **triton-ascend 3.2.2+dev** 下取得的。

> `K4` 在 `T % 64 ≠ 0` 的 case 上触发 AI Core vector trap（507015），从 `B_T1023` 起级联污染整轮回归，

> fp16 树恢复 **627/636**，失败清单与 fp32/bf16 完全一致。
> 触发条件、定位过程与 workaround 见 `TEST_REPORT_RETEST_20260923.md` §6。
>
> 因此 **3.2.1 交付口径下的最终结论**：fp32 627/636、bf16 627/636、
> fp16 **627/636（需 workaround；原树 431/636）**。

**最终态三棵树的失败清单完全一致，共 9 行，全部是先前已有的声明式限制**：

```
A_B4_H8_T131072  K2 / K3 / K4 / K6   grid(flattened)=65536 超过 NPU coreDim 上限 65535
D_KV32_H4_T4096  K1 / K2 / K3 / K4 / K6  K=32 不支持（BK=32 时 tl.dot 不稳定）
```

**无一条为本次改动引入的数值回归。** 依据：

* 剩下的 9 行**都不是数值比对失败**，而是 `不支持`：`_kernel_supports` 预检直接返回，
  kernel 根本没启动，`max_diff` 字段里写的是原因文本。
* `A_B4_H8_T131072` 的 grid 超限：K2/K3/K4/K6 的展平公式本次未改，确实超限；
  K1 已由 §1 的一维 grid 解除（该行现为实测 OK）。
* `D_KV32_H4_T4096` 的 K=32 限制：K1/K2/K3/K4/K6 的 K=32 路径本次均未触碰。

状态 ① 里 fp16 那 8 行 `K4 nan` **不是本次迁移引入的**，可静态证明：
`bench.py:_derive_inputs()` 的链全程用 **torch** 版本算子（`k1_torch`…`k5_torch`）
派生各 kernel 输入，triton 版从不参与链式派生；且交付基线的 K4 文件也**未**被迁移改动。
即 K4 那一行的代码与输入都和迁移无关，结果不可能因 K1/K2/K3 的改动而改变 ——
它是交付件自带的缺陷，已在 §5.3 单独定位并修复（状态 ③）。

#### harness 修正：`_kernel_grid_size()` 的 K1 分支

`bench.py:_kernel_grid_size()` 是 `_kernel_supports()` 唯一调用方，用途**仅**为预检
（不参与 grid 计算或启动），但它的 K1 分支写的是迁移前的三维公式
`cdiv(K,128)·cdiv(T,BT)·B·H`，于是 `A_B4_H8_T131072` 的 K1 行被一个**已不反映实际 kernel**
的预检拒绝。已改为跟随 kernel 的开关：

* `K1_MODE=1`（默认）→ 返回 `min(total, vector_core_num)`，与一维 grid 一致；
* `K1_MODE=0` → 返回原三维公式（保留 A/B 复核能力）。

修后该 case 由 1/6 行通过变为 **2/6**（K1 实测 5.722e-06，K5 2.980e-08）。

## 7. 后续建议

1. **上报 D4**（循环内 block pointer 载入非确定性）是最有价值的一项 —— 它挡住了 3.75× 的 K2 收益，
   且已排除流水线/多缓冲两个常见诱因，有最小对照。若上游修复，K2 值得重测。
2. **fp16 树 `T%64≠0` 的设备 trap 需要处置**：交付口径（3.2.1）下 fp16 树 K4 在
   `T % 64 ≠ 0` 时触发 AI Core vector trap（507015），原树全量回归只有 431/636。
   已定位触发条件、确认**交付版 HEAD 同样复现**（非本次改动引入），并验证 workaround
   （`T%64≠0` 走 fp32 计算 → 627/636）。详见 `TEST_REPORT_RETEST_20260923.md` §6。
   是否要打进交付物，待决策。
3. **排查 K5 同类隐患（未改，仅记录）**：`turbo_delta_rule_h_kernel.py` 里 `p_v` 的 load/store
   带 `boundary_check=(0,)`，而同一循环里的 `p_w`、`p_k2`（block pointer 形状同为 `(T, K)`）
   **没有** —— `T % 64 ≠ 0` 时最后一个 chunk 会越过张量末尾读。§5.3 已证明这类越界读在
   fp16 下会真的出 NaN（K4 的 `beta` 就是这么炸的）；本次单跑复核 K5 在这些 case 上未 trap
   （`B_T1023` K5 独立进程 OK），属"尚未爆的同类隐患"。因为 K5 是链上第二大开销（11.43 ms），
   **不建议在没有阳性证据时改动**，故本次只记录：若后续出现 T 非 64 倍数的 fp16 精度异常，
   优先查这里。
4. **实验期开关与死代码已清理**：`K2_DOT_F32` 开关拆除（固化 fp32 dot，§5.2）、
   `_token_parallel_kernel_hm3` 从三棵树删除（它定义了但从未被启动，唯一引用是一句
   "不要用它"的注释；该注释记载的结论已就地保留）。早前记录的 K2 消融变体（v1~v13）已不在树内。
   保留 `K1_MODE=0`（一维 grid 的 A/B 回退路径，默认 1）与 `K3_NP`/`K3_HM`（交付配置项，默认已收敛）；
   `_migrate_exp/` 整个实验树未纳入版本管理，可整体删除。
5. fp16/bf16 树的其余精度余量（bf16 K2 6.03e-03、bf16 K3 5.83e-03 距门槛 1e-2 均不足 2×）
   建议纳入回归看护，避免后续改动把某一行顶出阈值。
6. 参考包 `interview_en_answer/REVIEW.md` §10 记录：`devcontainer_root_key` 是一把**活的私钥**，
   已随提交推到 `github.com:zhouhuaman/sglang`（commit `28a98dc935`）。建议轮换并清理历史。
